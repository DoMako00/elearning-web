## Safety boundary

The browser uses only `VITE_API_BASE_URL` and the Supabase publishable authentication configuration. It does not use private database access, a service-role key, or R2 credentials.

Phone is optional contact data only. It is not used as a login identifier or OTP destination. First-time activation does not require email; the Student links a real mailbox from Settings, and only a verified linked email can be used for future OTP login. The deployment's Supabase Auth project must allow anonymous sign-ins for the initial activation exchange.

## Batch 2 commercial boundary

Payments use the manual-review model only: an authorized Admin explicitly approves or rejects a pending payment review. There is no gateway, webhook, provider confirmation, or browser-created subscription state. Subscription and seat mutations are reconciled from the backend after every successful command; the browser never composes replacement as release plus assign.

## Batch 3 implementation notes

`adminAcademicApi.ts` is the typed HTTP adapter; `adminV2Mappers.ts` maps backend DTOs into the accepted V2 models; `adminV2ServerData.ts` loads server state and persists supported store mutations. `AdminV2Layout` overlays those server collections over the UI/local store and strips them from local persistence. The accepted page component hierarchy, layout classes, and animation logic remain the presentation source of truth; changes in the four pages are limited to API-backed creation actions and the shared loading/error state.

The backend currently exposes academic catalogue reads but no curriculum write commands. Its academic-unit payloads are modules and do not carry a universal Subject/Module discriminator because Medway/Elite/Nexus presentation rules vary by commercial Brand; the adapter therefore does not infer a Subject label from institution names. Instructor directory responses likewise do not persist email, phone, specialties, schedules, or performance; those values are not synthesized from fixtures.

## Admin Batch 4 — Content, Security, Overview, and fixture audit

Content uses `adminContentApi.ts` with the central authenticated client. Lesson Resource metadata maps into the existing Content V2 model; media inventory is joined by resource ID without exposing object keys or permanent URLs. Upload uses server-generated short-lived signed PUT or multipart URLs, then backend verification; publish and withdraw use the mounted media lifecycle. Local object-URL preview and local Content persistence are removed. Descriptions, original filename, lesson release schedule, and visibility are not represented by the current safe API and are not claimed as saved.

Security uses persisted `/v1/admin/security/events` and the existing safe Student detail device/session projection. Account restore is a real Student status mutation. Device/session revocation and Admin device replacement remain disabled: current mutation routes require an internal app-user identifier not returned to the Admin UI, and no safe replacement-registration command is mounted. No fixture security events are created.

Overview uses the server aggregate for active subscriptions, grants, pending reviews, and operational counts; Student/course counts and payment-state summaries come from authenticated list APIs. Revenue and time-series trends are unavailable from the current aggregate API and are not estimated. Recent activity comes only from persisted security events.

Final Admin data-source audit: `adminV2.fixtures.ts` remains as a legacy initial-data/static-label module, but `adminV2.store.ts` strips all server-owned domain collections before storage and the operational pages overlay API data. `brandName` is a static display-label helper. `BRAND_FILTER_STORAGE_KEY` stores only the selected brand filter (UI state). The old `greenlearn.admin-v2.local.v1` store has all domain collections cleared and is not an authority for integrated pages; the reset action clears that local cache only. Synthetic `Local Admin` audit generation was removed, and the Notifications control now states that notifications are not available instead of displaying a fixture count. Semester Offering aggregate APIs remain ready, but there is no accepted dedicated Semester Offering frontend route; no new page was added.

Unintegrated/unsupported references are explicit rather than silently substituted: Curriculum writes; Instructor schedule/performance/contact metadata; lesson release scheduling and visibility; Admin protected-media preview; profile-scoped Admin device/session revocation and replacement; notification data. Remaining static/UI-only references are `brandName` display labels, the persisted brand filter, and the cache-reset affordance. The legacy fixture file itself remains but is not a runtime domain-data source for integrated Admin pages. No listed Admin V2 domain page uses fixture records for its integrated server-owned domain state. Separately, the pre-existing `/student-preview` route is a visibly labeled local demo flow and remains outside this Admin-only batch.
