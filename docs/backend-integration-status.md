## Safety boundary

The browser uses only `VITE_API_BASE_URL` and the Supabase publishable authentication configuration. It does not use private database access, a service-role key, or R2 credentials.

Phone is optional contact data only. It is not used as a login identifier or OTP destination. First-time activation does not require email; the Student links a real mailbox from Settings, and only a verified linked email can be used for future OTP login. The deployment's Supabase Auth project must allow anonymous sign-ins for the initial activation exchange.

## Batch 2 commercial boundary

Payments use the manual-review model only: an authorized Admin explicitly approves or rejects a pending payment review. There is no gateway, webhook, provider confirmation, or browser-created subscription state. Subscription and seat mutations are reconciled from the backend after every successful command; the browser never composes replacement as release plus assign.

## Batch 3 implementation notes

`adminAcademicApi.ts` is the typed HTTP adapter; `adminV2Mappers.ts` maps backend DTOs into the accepted V2 models; `adminV2ServerData.ts` loads server state and persists supported store mutations. `AdminV2Layout` overlays those server collections over the UI/local store and strips them from local persistence. The accepted page component hierarchy, layout classes, and animation logic remain the presentation source of truth; changes in the four pages are limited to API-backed creation actions and the shared loading/error state.

The backend now supports writes to the existing academic catalogue entities with idempotency, optimistic versioning, authorization and audit reasons. Academic modules remain the persisted unit entity; the UI does not create a second Subject table. Instructor directory metadata persists only the accepted public email and specialties; unsupported phone, private office hours, ratings and reviews remain blank/unavailable rather than synthesized.

## Admin purchase data-source correction

The manual-payment purchase wizard reads Students and Semester Offerings only from the authenticated Admin APIs. The UI-only `all` Brand filter is omitted from the Student list request (it is not a valid persisted Brand code), Brand comparisons are normalized, and candidate rows must match a real saleable Offering's Brand and academic placement. Arabic-script Student names are transliterated for Admin display without changing the stored profile name. Clearly test/acceptance-labeled rows are not eligible for purchases. No production Student or commercial records were deleted or changed by this frontend correction.

Student Home, My Courses, and Course Detail no longer fabricate courses, enrollment, lessons, media readiness, or access. They query the mounted Student course API with the accepted provider bearer session. Course artwork remains static presentation only; course identity, counts, scope, and access state come from the server.

## Admin Batch 4 — Content, Security, Overview, and fixture audit

Content uses `adminContentApi.ts` with the central authenticated client. Lesson Resource metadata maps into the existing Content V2 model; media inventory is joined by resource ID without exposing object keys or permanent URLs. Upload uses server-generated short-lived signed PUT or multipart URLs, then backend verification; publish and withdraw use the mounted media lifecycle. Local object-URL preview and local Content persistence are removed. Descriptions, original filename, lesson release schedule, and visibility are not represented by the current safe API and are not claimed as saved.

Security uses persisted `/v1/admin/security/events` and the safe profile-scoped Student device/session projection. An authorized Admin can revoke Student sessions or a device and its active sessions, or authorize a one-use device-replacement exception from the Security dashboard; each sensitive action requires a reason, permission, and idempotency key, and refreshes server state. Student device revocation remains unavailable as a self-service action. No fixture security events are created.

Overview uses the server aggregate for active subscriptions, grants, pending reviews, and operational counts; Student/course counts and payment-state summaries come from authenticated list APIs. Revenue and time-series trends are unavailable from the current aggregate API and are not estimated. Recent activity comes only from persisted security events.

Final Admin data-source audit: the old `adminV2.fixtures.ts` file has been removed. `adminV2.defaults.ts` contains only empty collection defaults and static brand labels; `adminV2.store.ts` is memory-only and strips server-owned collections. `BRAND_FILTER_STORAGE_KEY` stores only the selected Brand filter (UI state). Synthetic `Local Admin` audit generation was removed, and the Notifications control states that Admin notifications are unavailable instead of displaying a fixture count. Semester Offering management is exposed in the existing Subscriptions route; no separate page or navigation destination was added.

Curriculum writes now use existing academic catalogue records and the audited command path. Assessment attempts support a dedicated Admin score override while preserving the original calculated score. Platform owners can assign one existing Admin role using versioned/idempotent audited commands with last-owner protections. Instructor public directory metadata persists only the accepted UI's public email and specialties; ratings/reviews, personal phone, and office availability remain unmodeled. Device revocation remains Admin-only and direct; Student Settings cannot revoke or request device revocation. Remaining static/UI-only references include `brandName` display labels and the persisted Brand filter. `/student-preview` remains a visibly labeled local demo flow.
